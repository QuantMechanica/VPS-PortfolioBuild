# MNT-002 — Live-Session-Supervisor: Queue-No-op statt bestätigtem Start

Autor: Codex  
Korrigiert nach Review Claude 2026-07-28

## Problem

Die bekannte Contract-Drift-Erklärung ist real, aber nicht hinreichend:
`QM_T_Live_AtLogon` und `QM_FTMO_AtLogon` erlauben Demand-Starts, obwohl
`T_Live_Watchdog.ps1` sie verbietet; der
`QM_Live_MT5_SessionSupervisor` hat zwei Trigger statt genau eines
(`tools/strategy_farm/T_Live_Watchdog.ps1:336-417`). Der Review-Snapshot zählte
3.659 `session_supervisor_start_blocked_task_contract`-Zyklen.

Step 0 zeigt jedoch den eigentlichen Ausfallpfad:

- `qm-admin` war in Session 3 `Disc`; der Supervisor-Task blieb `Ready` und
  lieferte am 28.07.2026 weiterhin `LastTaskResult=0x800710E0`.
- `D:\QM\reports\state\live_session_supervisor.json` wurde zuletzt
  `2026-07-26T15:34:18Z` geschrieben.
- `D:\QM\reports\state\live_supervisor_watchdog.log` enthielt beim
  Read-only-Snapshot 687 Zeilen mit `kicked`, aber keinen Fehler; der letzte Kick
  war `2026-07-28T21:15:06Z`, ohne neuen Heartbeat.
- Der zweite Watchdog ruft `Start-ScheduledTask` auf und schreibt unmittelbar
  danach `kicked` (`tools/strategy_farm/live_supervisor_watchdog.ps1:95-96`).
  Er bestätigt weder Action-Start noch PID/Session noch Heartbeat.

Damit bedeutet „kick erfolgreich“ nur, dass die Scheduler-API den Request
angenommen hat. Beim `InteractiveToken`-Task in der getrennten RDP-Session wird
der Start als `0x800710E0` gequeued/abgelehnt; ein Engine-Prozess entsteht nicht.
Die Entry-Skripte sind nicht von der vermuteten PS5.1-Stderr-Falle betroffen:
Supervisor und zweiter Watchdog nutzen
`$ErrorActionPreference='Continue'`, der Task-Start enthält kein `2>&1`
(`Live_MT5_SessionSupervisor.ps1:24-34`,
`live_supervisor_watchdog.ps1:28-35`). Es gibt beim Einstieg auch keine
Abhängigkeit von `G:`. Contract-Reparatur allein hätte daher das
Heartbeat-Kriterium nicht bewiesen.

## Lösungsvorschlag

1. **Step 0:** Einen Start nur dann als Erfolg werten, wenn innerhalb des
   Zeitfensters ein frischer Supervisor-Heartbeat mit passender
   `identity`, `session_id`, `supervisor_pid` und Scheduler-Ownership vorliegt.
2. Der Supervisor bleibt zwingend `qm-admin`/`InteractiveToken`; MT5-GUI-Prozesse
   dürfen nicht in Session 0 unter SYSTEM gestartet werden.
3. Der Task erhält genau einen `AtLogon`-Trigger mit `PT45S`, unendliches
   Execution-Limit, `RestartCount=255`, `RestartInterval=PT1M` und
   `AllowStartOnDemand=true` ausschließlich für den vorhandenen
   sessiongebundenen RunEx-Starter.
4. Der 15-Minuten-TimeTrigger wird entfernt. Der SYSTEM-Watchdog startet bzw.
   prüft den Supervisor über `Start_Live_SessionSupervisor.ps1` mit expliziter
   Session-ID; ein einfacher `Start-ScheduledTask`-Kick ist kein Recovery-Beweis.
5. Die Live-Task-Verträge werden mit dem unexecuted Paket
   `tools/ops/task_contract_fix_2026-07-28/` geändert; der Branch selbst
   registriert und startet keine Tasks.

## Akzeptanzkriterien

- `QM_Live_MT5_SessionSupervisor` hat genau einen Logon-Trigger, Principal
  `qm-admin`, LogonType `Interactive`, `AllowDemandStart=True`,
  `ExecutionTimeLimit=PT0S`, `RestartCount=255` und `RestartInterval=PT1M`.
- Nach einem OWNER-ausgeführten RunEx-Start wird
  `live_session_supervisor.json` innerhalb von 60 Sekunden erneuert; Identity,
  Session-ID und Scheduler-PID stimmen überein.
- Zwei aufeinanderfolgende Watchdog-Zyklen zeigen
  `session_supervisor_heartbeat_ready=true` und
  `session_supervisor_scheduler_owned=true`.
- Ein API-Kick ohne neuen Heartbeat wird als Fehler und nicht als Erfolg
  klassifiziert.
- Es wurde weder T_Live noch AutoTrading aus diesem Branch verändert oder
  gestartet.
