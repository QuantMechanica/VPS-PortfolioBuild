### Placement and configuration

The new draw is at `QM_BasketOrder.mqh:153-180`, after symbol, kill-switch, news, EA-id, magic,
and open-position duplicate checks and before price/lot resolution and
`QM_TradeContextSend`. It therefore satisfies the requested “after safety checks, before broker
round-trip” placement and mirrors the existing standard-entry hook at
`QM_Entry.mqh:258-270`.

`QM_FrameworkInit` resets the central seed before consumers and calls `QM_EntryConfigure` with
the configured stress probability (`QM_Common.mqh:133-137,213-214`). The shared global is thus
configured for current framework EAs; it remains a no-op at probability zero.

### Partial-open behavior

The two named live callers do clean up:

- `QM5_12778`: both legs are attempted at lines 289-290; failure of either calls
  `Strategy_ClosePair` at 297. Its exit path also flattens a non-two-leg package at 350-358.
- `QM5_13117`: both legs are attempted at 270-279; failure calls `Strategy_ClosePair` at 283.
  Its management path flattens a one-leg package at 324-330.
- `QM5_13140`, the builder's reference, opens the second leg only after the first succeeds and
  rolls back at 493; its management path also rejects invalid composition.
- `QM5_12821` counts planned versus opened legs and calls `QM12821_CloseAllOwned` when they differ
  (`682-721`).

The contract is not universal:

- `QM5_10009` loops over three legs, records only `any_opened`, and returns success if at least
  one leg opens (`290-326`). `Strategy_ManageOpenPosition` is empty. A stress rejection can leave
  a partial three-leg spread until a normal exit.
- `QM5_10025` opens both pair legs independently, records `opened=true` if either succeeds, and
  treats that as a valid entry (`450-461`). There is no immediate rollback.
- For such “any opened” callers, the claimed effective whole-basket rejection
  `1-(1-p)^legs` is not the probability that the package is rejected. At `p=0.10`, a two-leg
  any-open caller rejects the entire entry due solely to this hook with probability `p^2 = 1%`,
  and a three-leg caller with `p^3 = 0.1%`; the much larger event is a corrupted partial package.

There is also an existing duplicate hook. `QM5_20123` preflights every planned member with
`QM_RandBoolTagged("entry_reject", ...)` before opening any leg (`547-575`), then calls
`QM_BasketOpenPosition` per leg (`577-590`). With the WP-9 header, a two-leg package at 10%
accepts only if all four draws pass: `0.9^4 = 65.61%`, i.e. a 34.39% rejection rate rather than
the intended 19%. It does have rollback, but it is now over-stressed.

These counterexamples make the per-leg implementation a blocker as a blanket shared-header
change. The repair needs an explicit basket-level contract, or a complete caller migration/audit
that distinguishes atomic packages, independent rebalance legs, and callers with an existing
preflight.

### RNG tag and comparability

Tag reuse is deterministic but is not an independent per-tag substream. `QM_SeedRNG.mqh:28`
holds one global state. `QM_SeedAdvanceTag` XORs the tag into that state and advances it
(`63-69`); a tagged draw then advances the same state again (`102-111`).

An independent Python replay of those exact 32-bit operations produced these first five
`entry_reject` uniforms:

- seed 42: `0.984811029, 0.175664870, 0.528046972, 0.397405820, 0.575852599`
- seed 17: `0.068769791, 0.956430205, 0.590085834, 0.169842475, 0.527538543`

Thus the same tag in a different call position gives a different, repeatable next draw, as
intended for a sequence. Inserting a basket draw also shifts every later draw, including a later
standard-order `entry_reject` draw. `QM5_10309` is a concrete mixed caller: it opens its host via
`QM_TM_OpenPosition` (`437-480`) and its foreign leg via `QM_BasketOpenPosition` (`483-499`).

Consequences:

- Single-order-only EAs are unchanged because they execute no new draw.
- Basket and mixed-path EAs are intentionally not comparable to old Q06/Q07 results after the
  first affected basket attempt.
- The comments in `QM_SeedRNG.mqh` describing tagged consumers as independent “sub-streams” are
  stronger than the implementation. Call-sequence changes cross-couple consumers.

### Include order and compile implications

A parsed include graph from `QM_BasketOrder.mqh` reached 12 framework headers and found no cycle.
`QM_Entry.mqh` does not include `QM_BasketOrder.mqh`; include guards also prevent duplicate
definitions. All 174 current EA source files that include `QM_BasketOrder.mqh` include
`QM_Common.mqh` first, and `QM_Common.mqh` already includes `QM_Entry.mqh` and
`QM_SeedRNG.mqh`. The new direct includes are therefore redundant for all current EAs and do not
create an observed include-order hazard.

I did not compile, per review constraints. A header is compiled into each EA's `.ex5`; changing
the source header cannot change an already compiled/running EA without recompilation. Any rollout
of WP-9 requires rebuilding every affected EA and re-running the stochastic gates whose call
sequence changed.

- Relevant test suite:

  Result: 43 tests passed.

### Real-archive result

The five archived tester labels and report-effective seeds were independently reproduced:

| tester.ini label | report-effective seed |
|---:|---:|
| 42 | 42 |
| 17 | 42 |
| 99 | 42 |
| 7 | 42 |
| 2026 | 42 |

Calling `_recover_existing_seed_results` against the archived work-item root recovered only key
`42`; 17/99/7/2026 did not enter their labelled slots. This closes the original five-slot
laundering failure.

However, recovery is ordered newest-first and mismatch is only logged. On the real archive the
selected seed-42 evidence was the newest file labelled 2026, while the genuine label-42 summary
was rejected as a later duplicate. The regression test asserts only `sorted(recovered) == [42]`,
so it cannot detect this selection behavior.

### Blocking provenance regression

Before WP-10, `_result_from_existing_seed_summary` required a
`_q06_stress_harsh_seed<N>.set` label from the run's `tester.ini`. WP-10 replaces that check with
only `_effective_seed_from_summary_path(...) == seed` (`q07_multiseed.py:147-149`).

That proves the seed but no longer proves Q07 phase, HARSH stress, or even the presence of a
tester configuration. I constructed an isolated valid summary with matching
EA/expert/symbol/period/terminal and 100 trades, no `tester.ini`, no harsh setfile, and an HTML
file containing `qm_rng_seed=42`. Recovery returned key 42. This is a false Q07 recovery path.

The fix should retain both axes:

1. bind the summary to the expected Q07/HARSH seeded setfile (or an equivalent immutable dispatch
   identity); and
2. require that the bound report's effective seed equals the requested seed.

Prefer an exact label/effective match when resolving duplicates, or reject mismatched labels
entirely. Effective seed must be authoritative for the value actually run, but it is not a
substitute for phase/stress provenance.

### Regex, encoding, and report binding

The actual archived reports are UTF-16 LE with BOM, contain one input occurrence such as
`<b>qm_rng_seed=42</b>`, and parse correctly. The decoder also handles the test UTF-8 reports.
Localization does not alter the EA input name, so German report chrome is not a problem for this
regex.

The regex searches the entire HTML rather than the Inputs table:

- one input occurrence returned its seed;
- two identical occurrences returned the seed because values are collapsed into a set;
- conflicting values returned `None`, which is fail-safe;
- a comment-only document `<!-- qm_rng_seed=99 -->` with no Inputs table returned 99.

`_effective_seed_from_summary_path` also recursively scans all `report.htm` files below the
summary directory and returns the first unambiguous one, rather than binding to the report listed
in the accepted `summary.json` run. The one-report Q07 convention makes current archives work,
but the authentication primitive itself is permissive.

### Re-run and resume paths

An unauthenticatable recovered summary is skipped. In `main`, only recovered keys bypass
execution; every missing seed falls through to `_write_seeded_setfile` and `_run_seed`
(`498-526`). It therefore degrades into a fresh run, not an immediate `INVALID` aggregate.

There is one recovery function used for both the active report root and `.requeued_*` siblings,
and both pass through the effective-seed check. I found no separate resume path that bypasses it.

Fresh runs are a remaining end-to-end gap: `_run_seed` trusts the caller's `seed` field and reads
summary/report metrics, but never calls `_effective_seed_from_report`. A newly completed run can
therefore enter its requested slot without report-effective authentication. The setfile writer
now validates its own output, which reduces this risk, but it is not the claimed report-based
end-to-end check.

No tests were deleted or replaced in the scoped diff. Three existing recovery tests were adapted
by adding minimal reports, and two regression tests were added. The tests are green, but they do
not cover non-Q07/HARSH contamination, Inputs-table scoping, bound-report selection, fresh-run
authentication, or preference for the genuine label-42 archive entry.

## WP-11 — Q10 KS baseline parser

### Audit reproduction

```text
python framework/scripts/gen_q10_baseline.py --audit D:/QM/reports
```

It returned:

```text
audited=27  changed=27  self_divergent=17  missing=0  unparseable=0
```

I separately replayed the exact old row regex/“second-to-last decimal” algorithm and compared it
with named-column Profit values. The independent totals were:

- 27 reports / 6,569 closing deals;
- 24 reports had positional corruption;
- 2,380 deals were positionally mis-parsed;
- every one of the 27 stored Common distributions matched a replay of the old parser;
- 4,925 deals had Profit different from Profit+Swap+Commission, independently confirming that
  the gross/net mismatch is not reducible to the positional bug.

This reproduces all four WP-11 headline claims: 27/27, 24/27, 2,380/6,569, and 17/27.

### Named-column parsing against reports on disk

All 27 Q10 source reports were UTF-16 LE with BOM and used the same actual English deals header:

`Time, Deal, Symbol, Type, Direction, Volume, Price, Order, Commission, Swap, Profit, Balance, Comment`

They contained 6,568 `in` and 6,569 `out` rows. The named parser resolved all 27 with no missing or
unparseable report.

I also located and parsed actual German-header, UTF-16 reports on disk, including:

- `D:\QM\reports\pipeline\QM5_10440\Q08\_baseline\QM5_10440\20260602_191149\raw\run_01\report.htm`
- `D:\QM\reports\pipeline\QM5_10513\Q08\_baseline\QM5_10513\20260603_045359\raw\run_01\report.htm`

Their deals header uses `Zeit, Trade, Symbol, Typ, Richtung, Volumen, Preis, Auftrag, Kommission,
Swap, Gewinn, Kontostand, Kommentar`. The parser extracted 451 and 76 closing nets respectively.
The German reports on disk still use `out` for the row direction and `.` for the decimal mark;
the implemented aliases handle their localized header correctly.

The parser is materially stronger than the old positional heuristic. The actual on-disk variants
reviewed are covered. It still has no corpus proof here for French, UTF-16 BE/no-BOM, or reports
whose closing direction is `in/out`; those are listed under limitations.

### Net formula

`QM_Common.mqh:805-808` computes:

```text
net = DEAL_PROFIT + DEAL_SWAP + DEAL_COMMISSION
```

and feeds that exact value to `QM_KillSwitchKSOnTradeClosed` at line 835. `DEAL_FEE` is not read
anywhere in this live feed. WP-11's named Profit+Swap+Commission formula therefore matches the
live comparison quantity exactly, including the deliberate omission of fee.

### Fail-loud behavior and Q10 aggregate

`process_one` catches `ReportParseError`, prints a failure, returns `False`, and writes no
baseline. It also refuses distributions below the loader's ten-sample floor.

In `q10_confirmation.main`, the Q10 aggregate is written before baseline capture
(`q10_confirmation.py:280-281`). `trigger_baseline_capture` treats a nonzero generator exit as a
logged `False` result (`210-226`), and its return value is not used to change the Q10 verdict
(`285-290`). A parser failure therefore does not erase the aggregate, crash the parent, or turn a
Q10 PASS into FAIL/INVALID. The child fails; Q10 evidence survives.

There is no regression test for that caller-level failure path. Also, `audit_all` always returns
zero even when it counts missing or unparseable inputs; that is a useful hardening follow-up for
automation, though it did not affect this clean audit run.

### Blocking output-default / OWNER-gate defect

Read-only `--verify` and `--audit` branch before generation and do not write. `--out-dir` also
works for explicitly staged regeneration. The existing corrected staging directory contains 54
files (27 canonical `.DWX` names plus 27 broker-symbol aliases):

`D:\QM\reports\state\q10_baselines_regen_wp11_20260725`

The code is not safe by default:

- `BASELINE_DIR` is the live-readable MT5 Common directory
  (`gen_q10_baseline.py:70-72`);
- `write_baseline(..., out_dir=None)` selects it and creates/writes files (`230-254`);
- single and `--discover` generation leave `out_dir=None` unless the operator supplies a value
  (`527-542`);
- automatic Q10 PASS capture calls the generator without `--out-dir`
  (`q10_confirmation.py:210-220`).

Therefore I cannot confirm the requested statement that nothing writes into live Common by
default. The opposite is true. A routine automated Q10 PASS can publish a corrected baseline into
the path read by live EAs, ahead of the manual Q11-Q13/OWNER decision.

WP-11 should default to an evidence/staging directory or require an explicit publish/apply
operation for Common. The Q10 trigger must pass the safe staging output. Promotion of the already
regenerated files must remain a separate OWNER-authorized operation.

## Deploy-order implications

1. **Fix WP-9 before compiling or requalifying basket EAs.** Decide and encode the basket-level
   rejection contract, migrate non-atomic callers, and remove/suppress the QM5_20123 duplicate
   hook. Then recompile every EA that consumes the header. Existing `.ex5` binaries are unaffected
   until rebuilt.
2. **Deploy corrected WP-10 authentication before recovering or rerunning Q07.** Preserve
   Q07/HARSH dispatch provenance and authenticate both recovered and fresh reports. WP-9 changes
   the basket RNG call sequence, so basket Q06/Q07 evidence must be generated after the final
   WP-9 binary; old and new stochastic results are not comparable.
3. **Fix WP-11's safe output default before enabling normal Q10 capture.** Audit/verify may deploy
   independently because they are read-only. Keep the 54 regenerated files in the staging
   directory. Do not copy or regenerate them into Common until OWNER authorizes promotion.
4. WP-10 and WP-11 require no EA recompile by themselves. WP-9 does.
