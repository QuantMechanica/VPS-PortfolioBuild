Both rows carry the identical `source_repair_authority` string

## Root cause

The authority in question was registered by commit `162dc07c` ("generic evidence-bound
compile-fail repair registry, qm.compile-fail-repair-authority/v1 +
registrations QM5_41475/QM5_41477"), merged into the canonical checkout's working tree
at `dc8c5556d4` (merge of `agents/fable-compile-repair-20260918`) at
**2026-09-18T01:03:13Z** — i.e. **51s before** T3's claim-time recheck ran, and
**6m16s before** T10's.

`terminal_worker.py::_run_claimed_item` lazily imports the module on every claimed
COMPILE_EA row:

```python
try:
    from tools.strategy_farm import compile_work_items as _compile_work_items
except ModuleNotFoundError:
    import compile_work_items as _compile_work_items
```

This `import` statement executes every claim cycle, but CPython only reads a module's
source the *first* time it is imported into a process; every subsequent `import`
(including across different function calls, forever, for the life of the process)
just rebinds the name to the already-cached object in `sys.modules`. `terminal_worker.py`
runs as one long-lived process per terminal (T3 and T10 both started
**2026-09-17T10:10Z**, ~15h before the registry commit landed).

- If a terminal's worker process had already handled *any* prior COMPILE_EA claim
  before 01:03:13Z, its in-memory `compile_work_items` module is the pre-commit
  version, which has no knowledge of the QM5_41477 registry entry — every subsequent
  claim-time recheck in that process, for the rest of its life, evaluates against
  stale logic regardless of what's on disk. This is what happened on T3.
- If a terminal's *first* COMPILE_EA claim in its process lifetime happened to land
  after 01:03:13Z, its lazy import reads the current file and gets the new registry
  logic. This is what happened on T10 — not because T10 "restarted" or is a newer
  generation, but because its first `import compile_work_items` in this process simply
  happened to occur after the merge.

Both evaluations were internally self-consistent with the module version each process
had loaded; the divergence is a rollout-recency race, not a logic bug in
`classify_candidate` or in the generic registry mechanism itself
(`load_compile_fail_repair_authorities`, `_generic_compile_fail_repair_authorized`).
That registry-file read *is* mtime-checked and re-read fresh on every call
(`_COMPILE_FAIL_REPAIR_CACHE` keyed by `stat().st_mtime_ns`) — it is not the stale
component. The stale component is the enclosing Python module object itself, cached in
`sys.modules` by the worker process.

Note this is a distinct code path from the existing
`COMPILE_EA_WORKER_ROLLOUT_PENDING` / "release-on-restart ceremony" governance: that
mechanism holds *newly enqueued* COMPILE_EA rows (`release_on_restart=1`) until an
explicit restart cycle releases them, protecting the enqueue-time eligibility decision.
The **claim-time recheck** (`classify_candidate` invoked again synchronously inside
`run_compile_work_item` immediately before MetaEditor, as a safety net against changes
since enqueue) has no equivalent protection — it runs unconditionally with whatever
module version happens to be resident in that worker's memory.

## Fix applied this cycle (evidence-only, no gate/verdict logic changed)

`tools/strategy_farm/compile_work_items.py`: added `_module_staleness_diagnostics()`,
called from `classify_candidate()`'s return dict, so every future `candidate_recheck`
block in `compile_evidence.json` carries:

- `compile_work_items_module_path`
- `compile_work_items_module_loaded_mtime_ns` — frozen at first import into *this*
  process (module load time)
- `compile_work_items_module_current_disk_mtime_ns` — fresh `stat()` at evaluation time
- `compile_work_items_module_stale` — `true` iff the two mtimes differ, i.e. this
  process is provably running pre-change code
- `source_repair_registry_path` / `source_repair_registry_mtime_ns` — the specific
  registry file path and its current on-disk mtime, so a registry-entry-not-found
  result can be cross-checked against the registry file's own recency without git
  archaeology

This makes a recurrence of this exact divergence self-diagnosing from the evidence
file alone. No gate criteria, verdict logic, or authority-matching behavior changed.

## Worker restart policy (recommendation — not executed this cycle)

Root cause is generic: **any** edit to `compile_work_items.py` (or a module it imports
at module scope) is invisible to a running `terminal_worker.py` process until that
process restarts, for exactly the `sys.modules` caching reason above. This will recur
for any future compile-authority/registry change, not just this one.

Recommended policy: after any commit touching `tools/strategy_farm/compile_work_items.py`
lands on the canonical checkout, restart the T1–T10 `terminal_worker.py` processes in a
**staggered** sequence (one terminal at a time, waiting for each to reach an idle
between-claims point before restarting the next) rather than all at once. Staggering
avoids the all-terminals-down thundering-herd pattern already seen once
(2026-08-29, `project_qm_thundering_herd_worker_restart_2026-08-29`) and keeps MT5
saturation from collapsing to zero mid-restart. A worker that has not yet restarted
after such a change will now visibly report `compile_work_items_module_stale: true` in
its own `candidate_recheck` evidence, which gives the restart sequencer (or a human)
a direct, per-terminal readiness signal instead of relying on wall-clock-since-start
heuristics.

This policy is a recommendation only. Actually wiring a staggered-restart trigger into
the factory's worker-lifecycle automation touches live T1–T10 process management and is
left for a follow-on ops_issue/infra_repair task with its own blast-radius review,
per "no unstaggered worker restarts" and "do not interrupt active T1-T10 backtests
unless OWNER explicitly says so."
