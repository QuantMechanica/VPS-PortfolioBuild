## Implementation

### E1 — `framework/scripts/emit_dev_sweep.py`

Assembles a schema-valid `qm.opt-dev-sweep/v1` artifact from already-completed
categorical (`PREDICATE_ABLATION`) DEV trial runs. It never launches MT5 and never
selects a promotion candidate — `--chosen-trial-id` is a pre-registered input, not
a decision this script makes (Plan v2 E0-1: measurement is not selection).

- Reads the opt-card and trial ledger through `q15_freeze_check._validate_card` /
  `_validate_ledger` (reused, not reimplemented) to get `card_id`, the declared
  `predicate_trials`, `minimum_dev_fire_count`, `metric_name`, and
  `first_oos_start`.
- Requires one JSON result file per planned trial under `--results-dir`
  (`<trial_id>.json`); a missing file is a hard error ("incomplete trial set
  rejected").
- Cross-checks each result's `trial_id`/`predicate_id`/`direction` against the
  ledger's `planned_trials` entry byte-exactly; any mismatch is a hard error.
- `fire_count` is read as-is from the result file and is never defaulted; its
  absence is a hard error.
- `window.end` must be strictly before `card_info["first_oos_start"]`; a DEV
  window overlapping the sealed OOS folds is a hard error.
- The assembled artifact is checked with a dependency-free structural validator
  (`assert_matches_schema`) against `opt_dev_sweep.v1.schema.json`'s shape, then
  independently proven acceptable to the real consumer: the test suite feeds the
  emitted file through `q15_freeze_check._validate_sweep` (the exact function
  `q15_freeze_check.py` uses at freeze-check time) and asserts it validates,
  including the categorical eligibility/improvement/time-thirds selection logic.
- Output is canonical JSON (`indent=2, sort_keys=True`, no wall-clock, no
  randomness) — two runs against identical inputs are byte-identical.
- Dry-run by default; `--apply` writes to `--out`.
- Scope boundary: only the categorical surface is implemented. Numeric
  single-lever DEV sweeps are still small enough to hand-assemble and were not
  in the ticket's stated motivation (1386 census cells).

### E2 — `framework/scripts/emit_q16_lineage.py`

Assembles a schema-valid `qm.q16-lineage/v1` artifact (PARENT or CHALLENGER role).
No JSON Schema file exists for this schema anywhere in the repo — the contract is
the Python validators in `q16_head_to_head.load_lineage` /
`q16_head_to_head.validate_trial_ledger`, confirmed by direct inspection (both
functions read end to end) before writing this emitter.

- Binary/setfile/stream bindings via `q16_head_to_head._binding`; setfile risk
  contract validated via the real `q16_head_to_head._set_risk_contract`
  (RISK_FIXED=1000/RISK_PERCENT=0, matching `evaluate_q16`'s own requirement);
  stream path checked against `q16_head_to_head._is_mutable_mt5_storage`.
  Q10 evidence must itself carry `phase=Q10`/`verdict=PASS`.
- For `--role CHALLENGER`, the Q07/Q08 `trial_ledger_declared_count` /
  `observed_trial_count` values are **read from the bound Q07/Q08 evidence
  files**, never accepted as a CLI argument — there is no `--q07-declared-count`
  knob at all, only `--q07-evidence <path>`. Each is cross-checked against the
  trial ledger's own `declared_trial_count` before anything is written; a
  mismatch is a hard error (mirrors the exact invariant
  `q16_head_to_head.py:289-317` enforces downstream, so the emitter cannot
  produce something Q16 would reject).
- `selection_trial_count` is carried as a field distinct from
  `trial_ledger_declared_count` inside the emitted `q07`/`q08` blocks (an
  additive field `q16_head_to_head`'s validator does not read and therefore
  does not reject) — per Plan v2 E0-1, a pre-registered predicate has
  `selection_trial_count=1` even when e.g. 154 trials were measured. It is a
  required, explicit argument, never derived from or defaulted to the measured
  count.
- Every run self-checks the assembled bytes by materializing them to a
  temp file and round-tripping through the real `q16_head_to_head.load_lineage`
  (both roles) and, for CHALLENGER, `q16_head_to_head.validate_trial_ledger`
  against the actual trial ledger — before the artifact is ever written to
  `--out`. A CHALLENGER lineage that would fail Q16's own loader cannot be
  emitted.
- Deterministic canonical JSON output, dry-run by default, `--apply` to write.

### E3 — `framework/scripts/q14_opt_admission.py` cap pool isolation

`_existing_card_state` previously counted every open (`Q14 OPT_ELIGIBLE`, not yet
`Q16 done/failed`) card globally, with no `program_id` filter — a census program
and the 11 live wave-1 opt-cards shared one `max_concurrent_opt_cards` /
`max_cards_per_parent` counter (plan v2 A6 finding).

- `_existing_card_state` now takes a required `program_id` keyword and excludes
  any open Q14 row whose stored `payload_json["program_id"]` differs from it.
- `_decision_payload` now stamps `program_id` (from `config["program_id"]`,
  already required/validated by `validate_program`) into every Q14 admission
  row it writes, so the pool membership is derivable from the DB alone.
- A row admitted before this change (no `program_id` key in its payload) is
  conservatively counted toward **every** program's pool rather than silently
  dropped from cap enforcement — the isolation only excludes rows that
  positively declare a *different* program, it never weakens the pre-existing
  global safety net for un-migrated data.
- `build_plan`'s two call sites (`_existing_card_state`, `_decision_payload`)
  were updated to pass `program_id=str(config["program_id"])`.
