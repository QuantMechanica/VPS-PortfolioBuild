## Blocking findings

### 1. Card-invented Friday flattening destroys the monthly holding mechanic

The approved card requires monthly-only rebalancing and says to hold between monthly checks,
with only the hard stop active intra-month (`card:80-92`). The EA instead defaults
`qm_friday_close_enabled=true` at `QM5_12612_tsmom-12m-vol-scaled-ndx.mq5:37-39`, passes that
value into framework initialization at `:351-366`, and calls the Friday-close handler at
`:398-399`. The delivered backtest setfile does not override the Friday-close inputs
(`..._NDX.DWX_D1_backtest.set:17-30`), so the source default is effective.

This is an executable exit, not inert framework boilerplate: `QM_Common.mqh:649-662` returns
true from Friday 21:00 broker time when enabled, and `QM_Common.mqh:938-956` closes every owned
position. Because the EA latches the monthly rebalance key (`mq5:258-260,320`), a Friday close
also leaves it unable to re-enter until the next month. That changes multi-month TSMOM into a
short weekly fragment followed by flat time and is not card-faithful.

Named fix: set `qm_friday_close_enabled=false` for this swing strategy in source defaults and
the governed backtest setfile; preserve the card's monthly reversal/resize and ATR-stop exits.

### 2. Monthly cadence bypasses the canonical tester-robust helper

`mq5:63-80` hand-rolls a month key with `TimeToStruct` plus raw `iTime(D1,0/1)`, and
`mq5:258-260` reads raw `iTime` again to latch the rebalance. The raw reads carry locally added
`perf-allowed` comments, but an exact framework helper already exists:
`QM_Indicators.mqh:205-217,251-270` defines `QM_CalendarPeriodKey(PERIOD_MN1)` and
`QM_IsNewCalendarPeriod`, and `QM_Mod_AaZakMom12.mqh:93` demonstrates the governed monthly use.
The reviewer does not approve a raw-series exception where the canonical helper covers the
same contract.

Named fix: derive and latch the rebalance key through `QM_CalendarPeriodKey(PERIOD_MN1)` and/or
`QM_IsNewCalendarPeriod`, removing the duplicate raw calendar reads.

### 3. Realized-volatility buffer is input-sized without a bound or `ArraySize` proof

`strategy_vol_window` is a user input (`mq5:46`). The no-trade guard enforces only a lower
bound (`mq5:234-235`); there is no maximum. `Strategy_RealizedAnnualizedVol` copies the input
to `n`, calls unchecked `ArrayResize(log_returns,n)`, and then indexes the dynamic array
(`mq5:176-210`) without verifying the resize result or `ArraySize`. This misses the ticket's
explicit bounded-buffer and `ArraySize` guard requirement even though the narrow automated
D10 predicate accepts a resize-count/loop proof.

Named fix: cap all D1 data requirements to a documented constant, load one bounded closed-D1
batch, verify both the copy/resize count and `ArraySize` before indexing, and fail closed for
out-of-contract input values.
